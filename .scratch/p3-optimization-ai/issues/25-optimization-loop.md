## What to build

把纯算法的优化器接到真实的 Study 编排上，并把优化过程持久化。
这是 ADR-0009 的落地：**每个设计点 = 一个独立 Study，绝不覆盖已有版本**。

新建 `core/optimization_loop.py`：

- **优化会话**：创建时记录意图（目标/约束声明）、收敛配置（预算三元组）、
  设计向量声明快照 —— 全部落库，保证可追溯（"当初想优化什么"是记录在案的事实）。
- **设计点评估**：把设计向量经 `design_vector` 映射成 (参数集, 铺层)，
  再用 `run_study` 跑一个**独立 Study**，然后用 `objectives` 归一成评估结果。
  - 纯铺层变动的点要**跳过数模再生**（用 #22 的复用能力），并断言 CATIA 驱动未被调用
- **持久化**：新增两张表 —— **优化会话**与**设计点**（设计向量、目标值、约束状态、
  失败原因、关联 Study）。走既有 `Db.MIGRATIONS` 幂等新增，不改既有结构。
- **设计点 ↔ Study 关联**：使每个设计点的血缘能从优化会话一跳查到。
- **失败隔离**：单点评估失败（技术故障）记录原因后继续，不中断整次优化。
- **汇总查询**：返回各设计点的目标值、约束状态、可行性、失败原因、是否当前最优，
  并支持按「可行 / 不可行 / 评估失败」分组。
- **L2 门**：优化结束给出"建议采用的设计点"，但**采用与否必须由人批准**，
  复用既有 `approval` 状态机新增一个 audit gate；「维持原设计」也是合法决策。

## 关于 `approval` 的改动边界

只**新增** gate 常量与一个薄函数，不改既有状态机的转换表与既有 gate 语义。
P2 的审批行为必须零回归。

## Acceptance criteria

- [ ] 可创建优化会话并记录意图、预算、设计向量声明快照（可从库里读回）
- [ ] 每个设计点都是一个独立 Study（断言 Study 数量 = 评估的设计点数，且互不覆盖）
- [ ] 纯铺层变动的设计点**不产生新数模产物**，且 CATIA 驱动调用次数为 0
- [ ] 设计点与 Study 的关联可查，设计点的血缘能从会话一跳回溯
- [ ] 单点技术故障不中断整次优化，失败原因在汇总中可见
- [ ] 汇总给出目标值/约束/可行性/是否最优，且能按三类分组
- [ ] **优化方案未经人批准时不可被当作"采用方案"**（断言拒绝）
- [ ] 「维持原设计」是合法决策且被记录
- [ ] 数据库演进不破坏 P1/P2 既有数据（构造旧库断言仍可查）
- [ ] P2 审批行为零回归（既有审批测试全绿）
- [ ] Python 3.8 兼容
